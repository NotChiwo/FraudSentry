## 2. V7.1 concerns: reproduced

### Concern 1: false "edited copy" after a re-capture. **NOT REPRODUCED in this test; the risk remains by construction**
Method: 49 genuine receipts (every one with a hand-labelled reference and amount). Each got two degraded copies, made in Chromium's canvas: **0.6× JPEG q0.7** (like a chat-app forward) and **0.8× PNG**. That makes 98 copies, each run through the app's real 3-pass OCR and compared with the original's scan via `matchAgainstHistory`.

| Outcome | 0.6× JPEG | 0.8× PNG | Total |
|---|---|---|---|
| reused (correct: same receipt recognised) | 40 | 41 | **81 / 98** |
| none (missed: reference not read on one side) | 9 | 8 | 17 / 98 |
| **edited-copy (false Critical)** | 0 | 0 | **0 / 98** |
| **same-moment (false High)** | 0 | 0 | **0 / 98** |

The amount was read identically on every copy and its original.

Limits:
- These are *simulated* re-captures (rescaled and recompressed), not a second real screenshot taken on a different phone.
- 49 receipts are too few to rule out a rare misread.
- The code still decides "edited copy" from one final amount per scan. Hardening it is cheap: keep the per-pass amounts in history and require the difference to appear in at least 2 passes on both sides. I recommend doing that, with a test.
- New observation: in 6 of the 17 misses, the reference was read on the original but **not** on the smaller copy. So reuse detection weakens on low-resolution forwards.

### Concern 2: "same recipient, same minute" on genuine payments
- In the 62-receipt corpus: 1,891 pairs, 158 with the same recipient name, 35 with the same recipient **and** same date. **0** were flagged.
- That is too few to estimate a rate. The real exposure is a seller receiving several payments in the same minute (e.g. a live-selling session). **There is no data for that.**
- Also, by construction: a re-scan of the *same* receipt whose reference is OCR'd 2+ characters differently, with the same name/date/minute, *will* hit this rule. Concern 1's data covers that path.

### Concern 3: future-date Critical vs device clock. **CONFIRMED**
Receipt "Oct 6, 2026 9:00 AM", true time 09:05 PH, running the real `checkReceiptDate`:

| Device clock | Result |
|---|---|
| correct / 6 h behind / 2 days ahead | ok |
| **13 h behind / 1 day behind / 1 year behind** | **future → false Critical** |

The device time zone does **not** matter: tested with `TZ=America/Los_Angeles` and `Asia/Tokyo`, the same instant is parsed either way. The receipt is assumed to be in PH time (UTC+8). The weak point is a wrong device clock.

**Proposed fix:** downgrade to High; reword it to "dated after your device's current time — if your phone's date is wrong, ignore this"; add a skew test.

### Concern 4: README vs TESTING on `npm audit`. **CONFIRMED**
README line 38 says `npm audit # must report 0 vulnerabilities`, which is false today. CI runs no audit at all. **Fix:** README → `npm audit --omit=dev` must be 0; CI step `npm audit --omit=dev --audit-level=high`.

## 3. New problems found (not in your list)

1. **ELA gives a "high" finding on most genuine receipts.** I ran `analyzeForensics` on all **63** images in the receipt folder (43 JPEG, 20 PNG; believed genuine apart from the unknowns above): **"Error Level Analysis (high)" fired on 39 / 63 (62 %)**, including **16 / 20 PNG screenshots**. The threshold (`hotspotPct > 4.5`) sits inside the normal range of genuine images (2.0–17.5 %). Each firing adds 0.28 to the rule score. **This is a false-positive generator** and it weakens the "every score explained" claim.
2. **"JPEG Encoding Mode (progressive)" fired on 31 / 43 genuine JPEGs**, and "EXIF missing" on 16. Chat apps and downloads re-encode images, so these flags carry almost no information but still add to the score.
3. Because of 1 and 2, a clean GCash receipt scores **0.38 on the rules** and a genuine MariBank receipt **0.44** (just under High). The low blended scores so far come mostly from the demo forest pulling them down. Once the forest is trained on real data, these false flags will matter more.
4. **Reference-format false positive.** The genuine MariBank receipt's reference really is `223435` (6 digits, per the hand label). `validateReference` in `imageVerification.ts` demands 8–20 characters, so it raises **"Reference Number Format (high)"** on a correct read. The check should use the per-issuer `REF_FORMATS` that `fieldValidation.ts` already has.
5. The results-screen heading order (h1 → h3) and 49–56 sub-12 px labels (see §1).
